## Decided tonight, not yet built

### Shell: persistence **and** panes

The user answered: **both**. That makes it a milestone, not a TODO item, and it supersedes the
open question in `plan/TODO.md`.

What it requires, roughly in order:

1. Move the `Pty` from a local in `connect_and_serve` up to `RelayCtx`, so it outlives a
   reconnect. Today it is a local *on purpose* — dropping it kills the shell and, via SIGHUP,
   whatever it was running.
2. Server-side scrollback with a cap, replayed on reattach. The client's xterm.js buffer dies
   with the page, so the server has to be the one that remembers.
3. **A kill rule.** A shell that survives every disconnect and is never reaped is exactly the
   process leak `proc::terminate` and the SIGTERM handler were written to close. Needs an
   explicit answer: killed on session stop, on daemon exit, after an idle timeout, or never.
4. A pane model on both sides — a tree of PTYs, per-pane sizing, and a focus concept in the
   client. This is the larger half.

⚠️ Interaction worth writing down now: `viewer_watchdog` (`ecbb4c0`) stops a session after 45 s
with no viewer, but leaves the relay socket up — so a persistent shell would survive a session
teardown while its windows vanish. Whether a detached shell should outlive the compositor session
that hosted it is part of decision 3, not a detail.

## Blocked on a measurement that needs a live session

- **dmabuf's cost (O7)** — needs a matched A/B against the `checkpoint-pre-dmabuf` tag, which
  means building an old commit and swapping the daemon twice. The saving lands in host CPU and
  inside the client's texture upload, **not** in any stage `timing.rs` breaks out, so the metric
  is a `/proc/<pid>/stat` utime delta with the `compositor session active` lines identical. Not
  worth two builds and two session kills while the machine is under test.
- **VBV A/B for R1** — the only remaining live hypothesis for 720×1614@120 dropping frames now
  that the decode theory is dead. Needs the bitrate pinned and a human driving the client.
- **Build starvation (R2)** — requires deliberately saturating 20 cores during someone's session.
  Antisocial tonight; the `runq_ms` field is already deployed and waiting.
- **`runq_ms` itself** — **n = 1** (`runq_ms=0` on a 162 ms stall). Consistent with "not CPU",
  nowhere near enough to close the branch point or demote `WADO_APP_CPU_WEIGHT`. The new
  percentile line should generate the volume.

## Deliberately not done

- **`wp_fifo_v1` / `wp_commit_timing_v1`** — deferred on a **real blocker**, not on value. Both are
  promises about *when* the compositor latches a commit, and honouring either means the render
  tick must be able to withhold a ready surface from the composite it is already building — a
  per-surface barrier inside `render_output`. The tick composites whatever `space` holds when the
  timer fires and has no concept of "ready but not due". Advertising them without that barrier
  hands an app *wrong* pacing instead of none, which is the same trap `wp_presentation` had to
  avoid.
- **`wp_cursor_shape_v1`** — skip permanently, confirmed: `SeatHandler::cursor_image` is an empty
  body and nothing draws a pointer, so both halves of the protocol are no-ops here.

⚠️ **One thing to remember if the next session regresses:** `wp_content_type_v1` put a
`content_type_log.observe(surface)` call on **every** `wl_surface` commit — subsurfaces and popups
included. It is a `with_states` plus a hash lookup, so the cost should be nil, but it is a new call
on the commit hot path and therefore the second variable in the same daemon swap as
`wp_presentation`. If frame timing moved, that is the cheap one to rule out first.

### Superseded — these four landed

- **`wp_presentation`** (`7f551e2`), **`xdg_activation_v1`** (`4667693`),
  **`wp_content_type_v1`** (`002fc97`), **`wp_single_pixel_buffer_v1`** (`7b5c5e3`).
  `wp_content_type_v1` is advertised and logged only; nothing reads the hint.

The text below is kept because it records *why* `wp_presentation` was parked, which is still the
reason its implementation looks the way it does:

- **`wp_presentation`** — was blocked on not knowing the panel's refresh rate. R9 landed tonight,
  so it is now *unblocked but not started*. Still needs care: a wrong presentation timestamp
  actively misleads an app's pacing, which is worse than no timestamp.
- **`xdg_activation_v1`, `wp_content_type_v1`** — low value. Nothing in wado would act on either
  today. `wp_content_type_v1` becomes interesting only if the encoder learns to read the hint.
- **`wp_cursor_shape_v1`** — skip permanently. The pointer path here is cursorless.
- **Tokio worker cap** — remains rejected (R3). No measured problem, and `runq_ms` is what would
  produce one.
- **Unbounded `SessionConfig.width`/`height`** — a client can request 100000 × 100000 and OOM the
  daemon. A DoS behind the Remote-ID gate rather than a panic, so it was ranked below the panic
  class and left. **One clamp closes it** whenever someone decides the ceiling.
- **PTY survives a watchdog-triggered stop** — real, low blast radius. Folded into the shell
  persistence work above, where it stops being a bug and becomes a design question.

## Environment, not code

- **The cloudflared quick tunnel is the weakest link in the rig.** Four URL changes in one day,
  each needing a client push because `DEFAULT_RELAY` is a compile-time constant. A stable relay
  host — the roadmap's iteration 2/3 — removes this entirely. Until then, the first check on any
  connection failure is the tunnel, not the daemon; the commands are in
  `memory/shared/environment.md`.
- **WAN loss reached 62%** tonight and cost hours across three wrong diagnoses before the link
  was measured. `ping -c 15 -q 1.1.1.1` is now the documented first step.
