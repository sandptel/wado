## Refresh rate: the fps picker was a guess

There is no API for a display's refresh rate. `requestAnimationFrame` fires once per composite,
so the **median** gap between callbacks *is* the refresh interval — median and not mean, because
one dropped frame doubles a gap and would drag an average up by a whole rung.

`js/refresh.js` takes 60 gaps (~1 s), snaps to the nearest plausible panel rate from a table
(24…240 Hz) when within 8 Hz, and reports the raw rounded value otherwise. A backgrounded tab is
throttled to ~1 fps, which would measure as 1 Hz and cache a lie, so anything slower than 100 ms
per frame is **refused** rather than cached.

Shown as a line under the fps picker, with a warning when the chosen rung exceeds it:

> This screen refreshes at 120 Hz.
> *(and if fps > hz)* Above that, extra frames are never shown — and every frame gets fewer bits.

That second clause is the point. Choosing a rung above the panel is not a free upgrade — it
splits the same bitrate across frames the display never presents, which is the `bits_per_px`
figure getting worse for nothing.

**Unblocks** `research.md` R8 (`wp_presentation` / phase-locking), which was explicitly parked
on not knowing `R`.

## Resync: the last lever on jitter-buffer inflation

Every network hitch leaves the browser's playout buffer permanently ~5 ms higher (31–33 ms
before, 36–41 ms after; two hitches in one session). **Every playout-hint approach is dead** —
`jitterBufferTarget` is a floor honoured only up to what the browser's own timing model demands,
and the model is what moves. `0f66d04` deleted the code that tried.

The inflated state lives in the **receiver**, and a receiver is created per peer connection. So
a re-offer resets it by construction. `W.resync()` rebuilds the connection; the compositor
session is not tied to it, so windows, applications and the shell all survive.

**Deliberately manual.** An automatic re-offer keyed on a jbuf threshold fires hardest on a bad
link, where dropping the connection is the worst available move — the same mistake
`reassertPlayout` made one layer up.

## On-screen keyboard: the cheap 90% instead of the protocol

`zwp_text_input_v3` is a **dead global** without `zwp_input_method_v2` bound: smithay drops every
text-input request — `enable` included — when no input-method instance exists
(`text_input_handle.rs:209`). Advertising it alone produces a global apps bind, use, and get
nothing from. Making it real means wado becoming its own input-method client, i.e. a second
Wayland connection from inside the compositor process. That is a milestone.

wado already injects keys directly (`Wado::key`), so the entire problem was *"make the phone's
keyboard appear"* — and only a focused editable element does that.

Two things that made this more than a one-liner:

1. **The input cannot actually be invisible.** `display:none`, `visibility:hidden`, `opacity:0`
   and a zero-size box all make mobile browsers refuse to raise the keyboard. It keeps a real
   1 × 1 box, on screen, clipped with `clip-path`, with a transparent caret and `font-size:16px`
   (below that, iOS zooms the page on focus).
2. **⚠️ Android soft keyboards report an empty `KeyboardEvent.code`.** The existing mapper
   (`input_keyboard.js`) is code-based and would see nothing typable. Characters therefore come
   from the `input` event and are translated to evdev codes here, synthesising shift where the
   US layout needs it; only the keys Android *does* report as codes — Enter, Backspace, Tab,
   Escape, arrows — go through `keydown`.

The existing mapper also gates on `document.activeElement === video`, which the OSK input is
not, so it correctly ignores these and there is no double-send.

`blur` reports state back to Rust, so a back-gesture dismissal leaves the bar button honest
rather than stuck lit.

**Known gap:** the character table is US layout. A non-US soft keyboard will produce wrong
letters for anything outside ASCII.

## `zxdg_decoration_v1`: server-side, so windows are borderless

The user chose this shape. Worth recording *why it was a question at all*: the protocol's entire
value is the answer, so a wrong answer is worse than no protocol. Absent the global, toolkits
assume client-side decorations — so replying `ClientSide` is a **no-op**, and `ServerSide` is the
only reply that changes anything. Since wado draws no decorations, it means borderless.

Borderless is right here rather than a shortcut:

- The viewer is usually a phone, where a CSD titlebar spends scarce vertical space on a strip
  whose buttons are too small to hit with a finger.
- Those buttons are already redundant — maximize/minimize/close/cycle arrive over the remote
  input path, driven from the client's own control bar.
- Dragging does not need a titlebar either: long-press-drag is `WindowDrag`, which never
  involved one.

A client asking for `ClientSide` is told `ServerSide` regardless. That is allowed — the
compositor's configure is authoritative — and it is the point: an app insisting on its own
titlebar would otherwise reintroduce the strip this removes. GTK keeps its header bar, which is
application content, and loses only the frame.

## How this was verified, and what that does not cover

CI green is not evidence the code shipped. The deployed wasm was fetched and searched:

```
https://sandptel.github.io/wado/assets/wado-client_bg-dxhb4f6f173e1d9b15e.wasm   (7,910,420 bytes)
```

`oskToggle`, `wado-osk`, `CHAR_TO_EVDEV`, `measureRefresh`, `reportRefresh`, `W.resync`,
`refreshes at`, `Resync video`, `barbtn`, and the current tunnel hostname — **all ten found**.

That proves the code is *in the bundle the phone downloads*. It proves nothing about whether the
soft keyboard actually rises on your phone, whether the measured rate matches the panel, or
whether resync drops jbuf back to its floor. All three need a human with the device.

## What to check by hand

1. **Keyboard** — tap ⌨ in the bar. The phone keyboard should rise and the button light up.
   Type into a text field in the session: letters, digits, shifted symbols, Backspace, Enter.
   Dismiss with the back gesture and confirm the button goes dark on its own.
2. **Refresh rate** — open settings. A line under the FPS picker should name a rate. On the
   1080 × 2422 phone that has been sustaining 118–121 fps, expect **120 Hz**; anything else is a
   measurement bug worth reporting.
3. **Resync** — with a session running, note `jbuf` in the debug stats, cause a hitch (or wait
   for one), then press ⟳. jbuf should drop back to its floor within a sample or two. That is the
   measurement O9 is waiting for.
4. **Decorations** — start a session and look at Chrome. No titlebar, no shadow, no rounded
   frame; content should start at the very top. The header bar (tabs, address bar) stays — that
   is app content, not decoration.
